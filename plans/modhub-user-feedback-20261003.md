# ModHub 用户反馈调查与处理建议

调查日期：2026-10-03。范围：Cloudflare KV 用量提醒、批量更新版本列表读取失败。以下调查记录为实施前快照，处理结果见末尾的实施记录；ModHub 版本号保持 v1.2.2。

## 已核实的结论

1. 本轮提醒对应 KV 写入压力。Cloudflare 的分类统计显示，10 月 2 日 UTC 日内写入为 637 次，读取为 9,702 次；分别占免费额度的 63.7% 和 9.7%。统计未显示当天已超过额度，不能把提醒解释为已经停服。
2. 截图中的英文错误可以由旧版客户端超时机制产生，并不证明用户点击了取消。v1.2.1 已修复这条客户端路径，当前源码版本为 v1.2.2；截图没有该版本新增的游戏版本与已安装版本说明，倾向来自旧版，但用户版本与反馈时间未知，不能据此定论。
3. 生产历史接口确实存在失败响应。10 月 2 日 UTC 日内，按请求 ID 去重后 `/mod-releases` 有 3,296 次 200、43 次 429，另有 14 次日志未记录正常响应状态。429 在代码中由 GitHub 的 403 或 429 转换而来，仍需限流响应头区分配额、次级限流或其他拒绝原因。
4. KV 写入提醒与截图故障没有足够证据建立直接因果关系。现有证据分别支持写入预算偏紧，以及超时、上游拒绝和批量等待体验问题。

## 写入增长的代码原因

正常稳定目录、所有定时任务成功时，当前固定预算如下。失败、审核同步、按请求补刷及首次查询缓存会改变实际总数。

| 路径 | 当前频率 | 每次 KV 读 / 写 | 每日 KV 写入 |
| --- | --- | --- | ---: |
| `updateIndex` | 每 5 分钟 | 2 / 1 | 288 |
| `updateCatalog`，Wiki 抓取成功 | 每小时 | 2 / 2 | 48 |
| 固定预算合计 |  | 624 读 / 336 写 | 336 |

因此，即使访问量很低，正常定时任务也约占写入额度的三分之一。10 月 2 日总写入相对该理论预算多出 301 次，但不能全部归因于用户首次查询：其中也可能包含审核、维护、补刷和重复请求。

代码位置：`dolmod-site/wrangler.jsonc` 的定时配置；`release-worker.js:1197`、`:1245`、`:1289`、`:2195`。公开索引与历史接口保持 `no-store`，热历史页每次仍读取目录与历史 KV，共 2 次；冷历史页为 3 次读与 1 次写。ReadMe 命中为 2 次读，冷查询额外写 1 次。

仅在内存中运行的独立探针已复现：

- 同一冷历史页同时查询 10 次，模拟上游延迟 100 毫秒，得到 30 次 KV 读、10 次写和 10 次 GitHub 抓取，缺少并发请求合并。
- 同一热历史页查询 10 次，仍得到 20 次 KV 读，但没有额外写入。
- 查询 `page=100000` 至 `100009` 的空历史页，均返回 200，每页都写入独立的七天快照，共 10 次写入；历史接口没有独立限流。

这些是代码可复现的放大机制，不是线上恶意访问已经发生的证据。

## 截图错误的原因与现有修复

旧版内存探针在触发十秒定时器后得到 `AbortError`，没有错误代码，消息为 `The user aborted a request.`。当前同条件得到 `TimeoutError / RELEASE_TIMEOUT` 和明确的二十秒中文提示。

当前 `src/javascript/modhub-market-versions.js:141` 已为请求及响应体统一限时，区分超时与用户取消；`:260` 使用同来源六小时成功缓存，`:277` 在临时失败时使用明确标记过期的缓存，`:279` 为非社区来源保留 GitHub 直连回退。社区来源继续要求核验当前审核目录。该修复已有测试和 v1.2.1 更新日志记录。

服务端仍有异常原文直接展示的路径：`dolmod-site/release-worker.js:526` 设置十五秒上游超时，`:576` 补充错误代码，`:592` 直接返回 `error.message`。因此新版客户端仍可能显示上游英文异常。原始异常应保留为错误详情或诊断记录，主状态需要明确说明上游超时或暂时不可用。

另有写入额度耗尽后的降级缺口：ReadMe 在 `release-worker.js:377` 保存缓存失败时没有单独捕获异常，已成功取得的正文也可能整体报错。应像历史缓存保存一样，记录缓存写入失败后继续返回有效正文；本次统计未显示此故障已经发生。

当前批量选版在 `src/javascript/modhub-market-install.js:312` 串行读取；每项 Worker 二十秒加直连十秒的最坏等待可以累加。四项理论上可能约两分钟；这是最坏预算，并非线上实测。任意行读取中还会禁止全部重试和主操作，见 `:269`、`:277`。

## 建议的处理顺序

### 第一阶段：减少固定写入并改善失败说明

1. 对反馈用户建议升级现有 v1.2.2；收集 ModHub 版本、反馈时间、游戏版本和日志错误代码，以便关联线上请求。不要让用户仅靠反复点击重试排查。
2. 将版本轮询从 5 分钟改为 15 分钟，每小时目录刷新暂时保留。正常固定写入预算由 336 降为 144 次/天，减少 192 次，约 57%。这是理论节省，不是部署后的实测；新版本发现延迟会增加。无 GitHub 凭据时轮询仓库批次，完整周期为 15 分钟乘以批次数；有凭据的全仓库查询周期约为 15 分钟。
3. 轮询间隔、批次时钟和索引过期补刷阈值必须共同调整。当前批次时钟固定使用五分钟；仅改定时配置为十五分钟，会在批次数是 3 的倍数时漏检部分批次。当前索引过期阈值为十分钟，必须同步提高至至少二十分钟，避免用户请求在定时任务空窗补刷并抵消节省。保留补刷节流，检查定时与补刷交错时的写入。
4. 历史空页不再形成任意页码的长期 KV 写入；配合短时负缓存、可核验的分页终点和独立请求限流，避免不写 KV 后反复请求 GitHub。分页上限须允许合理历史访问，不能任意截断作者发布；终点不能只按筛选后空列表判断，因为该页可能只有预发布或其他产品，原始分页仍有后续内容。
5. 将上游超时归为明确中文错误代码与主状态，原始原因放在独立详情或日志中；新增详情字段时同步调整网站与 Mod 端解析。保留 `Retry-After`、GitHub 配额剩余量和重置时间等诊断信息；403 不能一概认定为额度耗尽。ReadMe 缓存保存失败仅记录日志，继续返回有效正文。

### 第二阶段：合并并发冷查询，保留实时目录核验

优先评估官方 Workers Cache 的内层缓存入口：外层网关每次继续核验 D1 的目录、下架与来源；内层缓存来源签名与页码对应的公开历史资料，利用同缓存键的请求合并减少 GitHub 抓取和重复 KV 写入。保持 KV 七天成功快照供临时上游失败回退，六小时复查，并继续明确标记过期。

必须显式关闭默认网关入口的 Workers Cache，而非只依赖 `no-store`；内部资料缓存键由服务器验证后的来源签名和页码形成，错误、下架或无法核验目录的响应不得作为成功缓存。慢查询返回后还须复核当前目录，防止查询期间改源或下架。不要把最终安装授权响应整段缓存六小时，也不要用跨请求共享未完成网络 Promise 的全局变量代替经过运行时验证的缓存机制。

历史内层缓存有效期按快照抓取时间加六小时的剩余时间设置，不能每次命中都重新获得六小时；过期回退只设短缓存。空页负缓存同样绑定来源签名与页码，超时和 429 不得伪装为确定空页。可另外缓存原始 KV 索引快照 30–60 秒，但外层必须仍合并最新 D1 审核状态；公开读取不逐请求重复写回旧快照，持久同步由审核与定时路径负责。原生缓存可能被提前驱逐，不同地区仍可能各自回源，不能保证全球只抓取或写入一次。

本地 Wrangler 4.134.0 的配置 schema 已包含 `cache` 和 `exports`；这只证明配置支持，不代表生产缓存效果已验证。上线前需做 Workers 运行时和隔离环境测试。来源：[官方网关与内层缓存示例](https://developers.cloudflare.com/workers/cache/examples/)、[配置方式](https://developers.cloudflare.com/workers/cache/configuration/)。

客户端可再增加最多两路版本读取与逐行独立重试，重试共用同一队列上限，保留用户选择、明确的整批取消、版本风险确认和统一安装计划。并发增加应在服务端请求合并或限流控制落实后启用，避免先把上游压力放大。用户取消不得通过缓存回退变成成功，关闭后不能继续更新界面。

Workers Cache 的内层调用仍需纳入标准 Worker 请求计费与额度预算，不能把请求合并等同于无限免费容量。来源：[原生缓存计费](https://developers.cloudflare.com/workers/cache/#pricing)。

### 容量保障选项

随着用户增长，可评估 Workers 付费计划作为容量保障。当前最低订阅费为每月 5 美元，包含每月 100 万次 KV 写入和 1,000 万次读取，超额另计；不能把它当作重复写入与 GitHub 限流的修复。本次未开通或调整付费服务。

来源：[Workers 官方计费](https://developers.cloudflare.com/workers/platform/pricing/)、[GitHub 官方访问限额与响应头](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。GitHub 凭据是否有效及实际限流原因尚未核验，不能声称只增加凭据即可消除全部 429。

## 后续实现的验收重点

- 15 分钟轮询在批次数 2、3、6 等场景覆盖全部仓库，补刷不绕回五分钟写入频率。
- 同一冷历史页的并发请求合并，核对实际上游次数和 KV 写入次数；失败后允许重试，不能留下永久等待状态。
- 改源、下架、固定附件失效和查询期间审核变化，均不能被热缓存绕过；上游临时失败仍可使用合法的七天快照并标记过期。
- 原始空页、筛选后空页和有下一页的共享仓库发布分别测试；空页查询及限流不能消耗长期 KV 写入额度。
- 超时、取消、403、429、响应体挂起分别有准确主状态与保留的错误详情。
- 批量取消停止全部请求；两路读取中逐行重试不重取其他成功行，旧操作的迟到响应不能覆盖新批次。
- 网站与 Mod 端继续共用索引与历史契约；不修改 `schemaVersion: 1`，除非另行说明兼容方案。

## 第一轮实施记录（2026-10-03）

### 已完成的修改

- 版本轮询调整为每 15 分钟，批次时钟同步调整；索引过期补刷阈值为 20 分钟，补刷保留 15 分钟节流。每小时目录刷新保留。正常固定 KV 写入预算由 336 降为 144 次/天，减少约 57.1%；失败、历史查询与审核维护仍会产生额外操作。
- 原始索引缓存 60 秒；历史资料按来源签名与页码进入 Workers 原生缓存。默认网关关闭缓存，每次仍核验当前 D1 目录，并在慢查询后再次核验来源与下架状态。公开读取不逐请求持久回写目录，定时与审核路径继续同步。
- 原始空页不写入长期 KV，仅短缓存 60 秒；筛选后空页仍保留真实分页状态。历史接口增加每客户端 IP 每分钟 60 次的独立限制，支持最多 1000 页；这是本服务边界，不是 GitHub 发布页数限制。
- 固定标签或精确附件确认失效后，通过新的 D1 来源状态表推进来源水位，使全部历史页的旧缓存失效。恢复与并发迟到响应均重新核验水位；状态不能核验时返回 503，禁止旧缓存回退。普通发布来源不额外读取这张表。网站、提取器与 Mod 端同步拒绝来源失效后的旧数据。
- 超时、用户取消、GitHub 限流与普通拒绝分别处理，界面提供中文主状态和独立原始错误详情；保留重试、配额响应信息。ReadMe 正文获取成功后，缓存保存失败继续返回有效正文。
- 批量选版最多两路读取，首批、分页与逐行重试共享上限；重试不重取其他成功行，保留用户选择、焦点与滚动位置。整批取消停止请求，关闭后的迟到响应不更新界面或缓存；客户端按来源清理全部历史页，并阻止旧请求恢复已失效缓存。

生产没有配置 `GITHUB_TOKEN`，当前公开轮询为 8 个批次。因此正常完整检查周期由约 40 分钟变为约 2 小时；失败可能延长周期。节省固定写入与版本发现延迟之间存在这一取舍。未变更付费计划，未增加查询凭据。
