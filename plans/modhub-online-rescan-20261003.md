## 建议的第二轮调整

### 优先级高：让实际定时执行遵守十五分钟预算

管理 API 的目标为十五分钟，但新版本日志在上线后仍收到旧 `*/5 * * * *` 触发。UTC 10:50:05–11:39 有 10 条成功五分钟触发及 1 条成功小时目录触发；UTC 11:20–11:45 独立重查仍有 5 条旧五分钟触发，且分组中的版本确认为新版；UTC 11:35–11:50 重查还有 3 条旧触发。尚未查明管理配置与触发分发不一致的根因。

`release-worker.js` 的 `scheduled()` 仅单独识别小时目录表达式，其他表达式全部调用版本更新。隔离模拟同一个十五分钟时段中的三次旧触发，产生 3 次 GitHub HEAD 与 3 次 KV 写入，批次相同。该模拟没有生产写入。

因此，144 次/天目前是目标配置预算，不能声称实际定时写入已经降至这一数值；旧触发还会重复检查同一批次。建议首先核对触发分发，再增加按事件计划时间判断的执行频率保护和跳过日志。不要仅以距上一快照写入的秒数判断，以免把正常十五分钟任务误延长为三十分钟。若新旧表达式同时到达，还须考虑同一时段的重复执行；单个实例的内存变量不能证明全局去重。

官方说明 Cron 配置传播可能需要最长约十五分钟，本次旧触发持续时间已超出这一描述，不能简单按正常传播等待解释。[Cron Triggers 官方说明](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

### 优先级高：GitHub 配额耗尽后等待重置

四条外显失败均带原始 403 和 `rateLimitRemaining: "0"`，支持主配额耗尽的判断。无凭据公共查询按出口 IP 使用有限额度；服务端与玩家 IP 限流不是同一预算。配置查询凭据能提高查询容量，但应使用独立、最小权限的服务端凭据，不能把本机既有凭据直接写入代码或浏览器。

当前实现保留了 `Retry-After` 和重置时间，却未据此停止再次回源。没有成功快照时，限流错误为 `no-store`，随后同页请求继续访问 GitHub；有合法旧快照时，短缓存最多缓冲 60 秒，下一次失效后仍可能在额度恢复前回源。

建议增加有界退避：按 `Retry-After` 或配额重置时间暂缓同来源查询，恢复后允许重试；仍可返回合法七天旧快照并标记过期。没有快照时继续返回明确限流错误，不能变成成功空页。开始可采用来源或页码的短期冷却，不必立即引入全局协调服务。配额为零时等待重置符合 [GitHub 官方限流处理要求](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。

### 优先级高：显式限制原生缓存的错误回退

这是代码与官方契约确认的缺口，尚未在生产做故障注入复现。两个内层成功响应目前仅设置 `public, max-age=...`；Cloudflare 原生缓存默认可能在 Worker 错误后持续返回旧缓存。外层收到内层 200 后只复核来源，未再次按 `fetchedAt` 核验六小时新鲜期及七天绝对上限。

KV 正常可读时，应用层通常会返回正确的 `stale: true`，但 KV 读取失败或快照已过期淘汰、上游同时发生 5xx/超时时，原生缓存可能用旧 200 替代错误，导致旧正文仍为 `stale: false`，甚至超过应用声明的七天期限。短空页缓存也需要明确这一边界。当前外层下架、改源与固定来源水位核验仍有效，本发现不证明安装授权被绕过。

隔离模拟内层返回 `200 / Cf-Cache-Status:STALE`，分别提供七小时与八天的合法同来源资料；现有外层均透传为 `200 / stale:false`。这确认了外层期限校验缺失，未模拟 Cloudflare 实际故障、没有生产写入，也不能据此声称玩家已收到八天旧数据。

建议两个内层缓存明确使用 `stale-if-error=0`，由应用层统一控制合法旧快照降级；外层再核验抓取时间，达到六小时标记过期、达到七天拒绝。实施时应在隔离的 Cloudflare Preview 进行真实错误回退验证，普通 Node 或模拟缓存测试不足以证明平台运行时行为。[Workers Cache 错误回退说明](https://developers.cloudflare.com/workers/cache/debugging/)

### 优先级中：统计被旧快照掩盖的上游失败

代码在转为旧快照之前未记录原始失败。隔离探针设置七小时成功快照和上游 `403 / remaining=0`，三次调用都得到 `200 / stale:true`，上游请求 3 次、警告记录 0 条；没有生产流量。线上原生短缓存会减少部分调用，但现有外显 429 统计仍不是全部上游失败数。

建议在选择旧快照时记录结构化诊断，包含目录、页码、原始状态、剩余额度、重置时间和使用旧快照的标记；避免每个热缓存请求重复记日志。保留现有成功降级行为。

本服务历史限流真实错误码为 `RELEASE_REQUEST_LIMITED`，上一轮报告的 `HISTORY_REQUEST_LIMITED` 已纠正。后续应与 `RELEASE_RATE_LIMITED` 分别统计。

### 已完成的代码调整

- 定时入口按事件计划时间执行十五分钟轮询，兼容仍在到达的旧五分钟事件；5、10 分钟等非轮询分钟、未知表达式、无效时间及迟到一个周期的事件在读取 KV 前跳过。按分钟判断保留正常计划时间的秒数偏移。版本查询前后核验已有快照所属时间段，减少同周期重复工作，并避免用迟到查询覆盖较新快照。
- GitHub 历史限流按 `Retry-After`（秒数或 HTTP 日期）及剩余额度为零时的重置时间冷却，最长一小时，缺少有效未来时间时为 60 秒。冷却只使用既有原生缓存，不增加 KV 写入或数据库表。没有快照时，私有内层保存限流封装，公开接口仍返回真实 429 与原始诊断；有合法旧快照时继续返回 `stale: true`，缓存期限截断至原抓取时间的七天上限。
- 两个资料缓存入口显式关闭平台错误回退，设置 `stale-if-error=0`；外层在重新核验当前来源后检查历史结构与原始抓取时间，六小时以上标记过期，七天及未来时间拒绝。限流封装过期、结构异常或身份不符同样拒绝，不当作成功历史。
- 选择合法旧快照时记录 `RELEASE_HISTORY_STALE_FALLBACK`，包含目录、页码、错误码和原始诊断，热缓存命中不重复记录。既有下架、来源变更、固定标签失效水位与恢复条件更新保持有效。
